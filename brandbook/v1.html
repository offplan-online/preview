Foundation

Design principles

Every UI decision is shaped by one overriding constraint: the product is a frame for high-quality architectural imagery. The UI must recede — not compete.

Recede from the render

The architectural render is always the hero. UI chrome should feel like museum labelling — informative, present, but never louder than the exhibit.

Warm, not cold

Stone, sand, and warm greys drawn from the renders themselves. Pure cool grey (#CCCCCC) or clinical blue-whites break the palette harmony when imagery changes.

Confident restraint

Premium brands use fewer elements, not more. One accent colour (gold). Two typefaces. Generous whitespace. No gradients on UI surfaces — leave those to the photography.

Status ≠ traffic light

AVAILABLE/SOLD/RESERVED are commercial states, not road signs. The current green/red/orange palette signals danger and congestion — wrong register for a luxury purchase decision.

Uppercase as texture

All-caps labels at wide tracking create visual texture and signal "UI layer" vs. "content layer." Used sparingly — navigation, buttons, status — not body copy.

White-label ready

Every token must override cleanly. A studio applying their brandbook swaps gold → their accent, navy → their primary, and the system holds. No hardcoded values in components.

Tokens

Motion

Premium products move with restraint. Fast micro-interactions, measured panel transitions. No bounce, no spring — those read as consumer/playful, not premium.

Micro 120ms ease-out Hover states, opacity, colour transitions
Panel 280ms ease-out Sidebar open/close, modal entrance
Page 200ms ease-in-out View transitions, filter result updates
Ease-out curve cubic-bezier(0.16, 1, 0.3, 1) All entrances — starts fast, settles gently
Ease-in curve cubic-bezier(0.4, 0, 1, 1) Exits — quick departure, no lingering
Implementation idea
The ease-out curve cubic-bezier(0.16, 1, 0.3, 1) is the same curve used in Radix UI and shadcn/ui — if the codebase already uses either, this is a no-op. The durations (120 ms / 280 ms / 200 ms) differ from Framer Motion defaults; a one-line override in the animation config is all that is needed. Product side just defines the feel; the tech team wires it in whenever makes sense.

Implementation idea
All four variants (plus Disabled) are best implemented as one component with a variant prop — e.g. <Button variant="primary | secondary | gold | ghost"> — rather than four separate components. Keeps usage consistent and lets future variants (icon-only, sizes) plug into the same API.
  • Library options the tech team might find useful: shadcn/ui Button (Radix-based, most flexible), Radix UI primitives (lower-level control), MUI Button (if already in the codebase), or Tailwind + class-variance-authority for variant management.
  • States — all five required: default · hover · active (pressed) · focus (visible ring for a11y) · disabled. Hover and focus often share visual treatment; active is a darker step.
  • Accessibility: visible focus ring is non-negotiable (WCAG 2.4.7), use aria-label for icon-only buttons, prefer aria-disabled over the native disabled attribute when the disabled control should still be focusable (e.g. with explanatory tooltip).
  • Gold variant guardrails: reserve for conversion CTAs only (Book Viewing, Contact Sales). If the codebase ends up with multiple golds on the same view, the variant is being misused — consider eslint rule or design review checkpoint.
